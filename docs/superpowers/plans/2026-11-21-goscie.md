# F17 Guests without an account — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A visitor registers for an event with name and e-mail only, confirms with a link from the e-mail, and can withdraw through a link.

**Architecture:** An unconfirmed request is not a registration: it waits in `guest_registration_requests` (hashed token, 24 h) and holds no place, so the capacity, waitlist and approval invariants (`docs/data-flows.md`) are untouched. Confirming runs a Better Auth plugin endpoint (the group-invitation pattern): the token proves the inbox, a passwordless verified user is found or created, `registerForEvent` registers with the stored answers, and the guest is signed in (ticket, certificate and GDPR export keep working). Withdrawal links carry an HMAC of the registration id, verified server-side; the link opens a page with a button (mail scanners follow GET links).

**Tech Stack:** Drizzle migration, Better Auth plugin endpoints (captcha plugin + our rate limiter), pg-boss e-mail job, TanStack Start routes, react-email, Vitest, Playwright + Mailpit.

**Spec:** [product spec F17](../specs/2026-11-19-produkt-design.md): "Zapis z potwierdzeniem e-mailem i rezygnacja z linku." Acceptance: "gość zapisuje się, potwierdza linkiem z Mailpit i rezygnuje przez link". The owner delegated design calls to Claude (21 November 2026).

## Design decisions (Claude's calls)

- **Who can register as a guest:**
  - Allowed: public events, and invite-only events opened with a valid invite link.
  - Not offered: "signed-in only" events.
  - Events requiring approval stay allowed: confirming creates a `pending` registration, as for signed-in people.
- **Questions:** the guest answers the event's questions on the form. They are validated when the request is made (same rules as `saveAnswers`), stored with the request and saved on confirmation.
- **Confirmation:**
  - The link opens `/{locale}/guest/confirm?token=…`, a page with a button that POSTs to `/api/auth/guest-registration/confirm`.
  - The token is single-use, 24 h, and stored as a SHA-256 hash.
  - After confirming, the guest is signed in and sent to the event page.
- **An address that already has an account:** confirming registers that account (the link proves the inbox). An unverified password set by someone else is removed first, as with magic links (`resetUnverifiedAccount`).
- **Withdrawal:**
  - Registration e-mails (confirmed, waitlisted, promoted, pending) get "Zrezygnuj z zapisu", linking to `/{locale}/registrations/{id}/withdraw?token={hmac}`.
  - The token is an HMAC-SHA256 with `BETTER_AUTH_SECRET` over `withdraw:{id}`, compared in constant time.
  - The page shows the event and a button. Withdrawing uses the existing `withdraw()` path, so places are freed and the waitlist promoted.
- **Abuse:**
  - The request endpoint is a Better Auth plugin endpoint, covered by the captcha plugin and `limitAuth`: 5 per IP + e-mail per hour, 20 per IP per hour.
  - Expired requests are deleted by the daily prune job.
  - The privacy clause (F9) is shown on the guest form.

## Review Focus

1. **A confirmation link opened twice or after 24 hours:** a clear "link used or expired" message with a way to register again, never a 500. (Task 4 e2e)
2. **The event filled up between request and confirmation:** the guest lands on the waitlist, and the e-mail says so. (Task 3 db test via `registerForEvent`, Task 4 e2e)
3. **A forged or edited withdraw token:** refused without revealing whether the registration exists. (Task 2 unit + Task 6 e2e)
4. **A guest form submitted for a signed-in-only or draft event, or an invite-only event without the link:** refused. (Task 3 tests)
5. **A mail scanner fetching the confirm and withdraw links** (plain GET): nothing changes until the button is pressed. (Tasks 5–6 e2e: `page.request.get` leaves the state unchanged)

### Task 3: Request endpoint

**Files:**

**Interfaces:**
- `POST /guest-registration/request`:
  - Body `{ eventId, email, name, locale, answers, inviteToken? }`, returning `{ ok: true }`.
  - Validates that the event is open, guests are allowed (not `authenticated`; `private` needs a valid `inviteToken`), and the answers.
  - Creates the request and queues the `guest-confirmation` e-mail in one transaction. It contains the confirm URL `{BETTER_AUTH_URL}/{locale}/guest/confirm?token=…`.
- `ensureVerifiedUser(adapter, email: string, name: string, method: string): Promise<User>`, extracted from the group-invitation plugin:
  - find the user by e-mail
  - if unverified: `resetUnverifiedAccount`, then set verified
  - if missing: create a verified user, handling the race
