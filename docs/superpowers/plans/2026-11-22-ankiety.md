# Ankiety po wydarzeniu (F20) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (inline). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Organizer adds survey questions to an event; after the event every participant who held a place gets an e-mail with a personal link, answers once, anonymously; the organizer sees a simple summary.

**Architecture:** Survey questions reuse `event_questions` with a new `form` column (`registration` | `survey`) and a new `rating` kind (1–5, survey only), so the admin editor, ordering and validation are shared. Answers live in `survey_responses` + `survey_answers`, which carry no registration or user id (anonymous; they survive account deletion and retention). `event_registrations.survey_answered_at` blocks a second response; `survey_emailed_at` makes the e-mail once-only, claimed by a 15-minute worker job exactly like certificate e-mails. The link is an HMAC of the registration id (same scheme as the F17 withdraw link), so guests without an account can answer too.

**Tech Stack:** Drizzle/Postgres, TanStack Start server functions, pg-boss, React Email, Paraglide, shadcn, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-19-produkt-design.md` (F20: „Ankieta po wydarzeniu z prostym podsumowaniem. Gotowe, gdy odpowiedzi uczestników dają poprawne podsumowanie”). Decisions below are the architect's (user delegated decisions, 2026-11-20/21).

## Decisions

- Who answers: registrations in state `registered` (held a place), at a `published` event that has ended (`effectiveEventEndSql`), with at least one survey question. Attendance is not required: many events never take attendance.
- Window: open from the event end for `SURVEY_OPEN_DAYS = 30` days. The e-mail goes once, only inside the window (switching the survey on later still reaches people while it is open).
- Anonymous: answers are stored without a link to the person; the summary never shows names. One response per registration.
- Summary: responses / people invited; per question — rating: average (1 decimal) and count per 1–5; choice and yes/no: count and percent per option; text: the latest 100 answers and the total.
- Editing questions after responses follows the F10 rule: a changed kind drops that question's answers, removed options drop their answers.
- Out of scope: reminders to answer, CSV export, a survey link on the account page, editing a response.

## Global Constraints

- TDD; `[F20]` Playwright tests seen failing first; admin screens designed for 360 px.
- UI text in `packages/i18n/messages/{pl,en}.json`, then `pnpm messages:compile`.
- Migrations only via `pnpm --filter @repo/db db:generate`; queue jobs inside the data transaction.
- No barrel files; `@repo/env` only; Biome.

## Review Focus

- A forged or other person's link must not open or submit a survey (token check before any lookup).
- Two submissions racing from the same link: exactly one response is stored.
- Waitlisted, pending, rejected registrations and cancelled events get no e-mail and cannot answer.
- Registration form must never show survey questions, and a `rating` question can never be a registration question.
- Summary queries stay bounded (no N+1, text answers capped).
